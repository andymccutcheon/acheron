## 1. What it is, in plain language

Helix Foundry is a local-first workspace for turning a company's operational data into a connected business model, rather than a memory or knowledge-retrieval server (`README.md:8-12`; `docs/GUIDE.md:25-37`).

One person runs it on one computer, connects databases, software-as-a-service APIs, files, or an ingestion API, and receives immutable Parquet snapshots plus profiles of those datasets (`README.md:103-111`; `apps/api/src/datasets.ts:19-79`).

It deterministically suggests an ontology by finding key columns, declared foreign keys, and matching values across sources; the person can rename or exclude entities before publication (`docs/GUIDE.md:50-60`; `apps/api/src/discovery.ts:285-365`).

An optional large language model can answer questions by generating read-only Structured Query Language (SQL), or propose pipelines, ontology types, dashboards, and actions; generated work is schema-checked and executed before it can be published (`docs/GUIDE.md:111-125`; `apps/api/src/assistant.ts:806-897`; `apps/api/src/assistant.ts:1237-1250`).

The default model is a digest-pinned local Qwen3 4B model through Ollama; Claude and OpenAI are explicit alternatives, with no cross-provider fallback (`docs/models.json:1`; `apps/api/src/providers.ts:28-93`; `apps/api/src/providers.ts:222-237`).

Users work through a React web application. Developers can use a workspace-scoped Hypertext Transfer Protocol (HTTP) application programming interface (API), OpenAPI document, or TypeScript software development kit (SDK) (`apps/web/src/main.tsx:44-95`; `apps/api/src/app.ts:95-106`; `packages/sdk/src/index.ts:69-96`).

It is not a Model Context Protocol (MCP) server and contains no embedding, vector-index, semantic-retrieval, or reranking subsystem. INFERRED from the complete tracked-source search for `mcp`, `embedding`, `retrieval`, `rerank`, and `vector`, plus the implemented interfaces enumerated in `docs/GUIDE.md:127-150` and `docs/API.md:1-5`.

## 2. How it works

### Components and responsibilities

- **Web application (`apps/web`).** `main.tsx` boots React, TanStack Query, routing, lazy-loaded Data/Ontology/Analyst/Workspace areas, onboarding gating, and the live-activity shell (`apps/web/src/main.tsx:1-64`; `apps/web/src/main.tsx:149-214`; `apps/web/src/main.tsx:240-257`). Its browser client calls JSON routes under `/api/v1` and relies on same-origin credentials (`apps/web/src/api.ts:1-27`).
- **API application (`apps/api`).** `server.ts` validates secrets, initializes storage, creates Fastify, listens, and optionally starts an in-process worker for development (`apps/api/src/server.ts:1-22`). `createApp` installs multipart limits, rate limiting, Swagger/OpenAPI, redacted logging, host/origin protections, token/workspace authorization, static web serving, and the area route modules (`apps/api/src/app.ts:63-134`; `apps/api/src/app.ts:137-177`; `apps/api/src/app.ts:420-445`).
- **Background worker (`apps/api/src/worker.ts` and `jobs.ts`).** The standalone entry initializes the same store and starts the worker (`apps/api/src/worker.ts:1-11`). The worker schedules source refreshes, claims queued or expired-lease jobs/runs, renews leases, dispatches handlers, retries ordinary jobs up to three attempts with bounded exponential backoff, and records terminal failures as findings (`apps/api/src/jobs.ts:14-24`; `apps/api/src/jobs.ts:32-100`; `apps/api/src/jobs.ts:101-180`). It is intentionally single-worker for this release (`docs/OPERATIONS.md:31-35`).
- **Executor service (`services/executor`).** The HTTP server accepts only an internal key, permits two active jobs and 50 waiters, spawns one child process per execution, caps it at 120 seconds and 10 megabytes of standard output, and gives the child only `PATH`, `DATA_DIR`, and the DuckDB memory setting (`services/executor/src/server.ts:6-24`; `services/executor/src/server.ts:25-75`). The child parses one job from standard input and calls the engine (`services/executor/src/runner.ts:1-9`).
- **Shared package (`packages/shared`, version 0.1.0).** It provides Zod schemas and TypeScript contracts for resources, providers, bundles, validation reports, onboarding, data, pipelines, ontology, analyst runs, and workspace views (`packages/shared/package.json:1-22`; `packages/shared/src/index.ts:14-26`; `packages/shared/src/index.ts:71-157`; `packages/shared/src/index.ts:229-354`).
- **SDK package (`packages/sdk`, version 0.1.0).** `FoundryClient` wraps the workspace API with bearer authentication, exposes onboarding, sources, ingestion, assistance, query, publication, graph-neighbor, action, rollback, and event-stream methods, and converts non-success responses to `FoundryError` (`packages/sdk/package.json:1-23`; `packages/sdk/src/index.ts:31-96`; `packages/sdk/src/index.ts:97-238`; `packages/sdk/src/index.ts:259-370`).
- **External stateful services.** HelixDB stores metadata and graph records; DuckDB processes immutable Parquet inputs; Ollama stores/runs the default local model (`docs/GUIDE.md:127-145`). Docker Compose defines separate app, worker, executor, HelixDB, Ollama, and model-initializer containers, with three persistent volumes (`compose.yaml:23-104`).

### Main data and analysis flow

1. A browser request without `Authorization` becomes the installation-local owner; a bearer token is looked up by SHA-256 digest and constrained to its workspace and optional read-only permission (`apps/api/src/app.ts:135-177`). First use creates the local user, non-expiring session, and initial workspace (`apps/api/src/app.ts:206-267`).
2. The user creates a source or uploads/ingests data. Connector credentials are encrypted before storage using AES-256-GCM with a key derived from `ENCRYPTION_KEY` (`apps/api/src/security.ts:11-39`). Connectors discover and stream MySQL/PostgreSQL, page REST APIs, download S3 objects, or delegate to Stripe, WorkOS, and PostHog adapters (`apps/api/src/connectors.ts:81-203`; `apps/api/src/connectors.ts:208-247`; `apps/api/src/connectors.ts:257-435`).
3. The worker claims the durable import job. The connector writes a complete staged file; the executor converts it to Parquet and profiles row count, duplicates, columns, examples, sensitive-name hints, candidate primary keys, and a multiplicity-sensitive fingerprint (`apps/api/src/data-jobs.ts:27-61`; `services/executor/src/engine.ts:137-198`). `ingestFile` creates an immutable version, keeps the former version active on schema drift, and records refresh/schema findings with evidence (`apps/api/src/datasets.ts:19-79`; `apps/api/src/datasets.ts:80-117`).
4. During onboarding, deterministic ontology discovery identifies likely keys, calculates exact and case-insensitive cross-column overlap in DuckDB, ranks declared/name/value evidence, merges one-to-one identities with union-find, and emits entities, links, match counts, notes, and a content hash (`apps/api/src/discovery.ts:285-365`; `apps/api/src/discovery.ts:367-471`; `apps/api/src/discovery.ts:473-512`; `apps/api/src/discovery.ts:658-713`; `apps/api/src/discovery.ts:803-840`). This is relational entity matching, not document retrieval.
5. For an Analyst request, the API persists a queued run with intent, authority, context, event history, and usage counters (`apps/api/src/assistant.ts:381-444`). The worker invokes `buildWorkspace`, which compacts dataset profiles, masks heuristic-sensitive sample columns for hosted models unless raw data is explicitly allowed, and invalidates saved checkpoints when input snapshot versions change (`apps/api/src/assistant.ts:484-556`).
6. With `intent: auto`, the model first routes to answer or build. Read-only callers are stopped before a build path (`apps/api/src/assistant.ts:775-804`). For an answer, the model emits a Zod-constrained plan containing one read-only SQL query and declared dataset inputs; code resolves only authorized datasets, executes the query in the sandbox, allows one model repair after an execution failure, and saves citations containing each dataset identifier, name, and immutable version (`apps/api/src/assistant.ts:806-892`; `apps/api/src/assistant.ts:893-963`).
7. For a build, either deterministic confirmed-ontology definitions or model-generated catalog/pipeline/ontology/dashboard groups become a typed `Bundle`. The server executes all pipeline and dashboard SQL, checks type keys and relationship match coverage, and gives failing generated asset groups at most two repair passes (`apps/api/src/assistant.ts:1180-1250`; `apps/api/src/assistant.ts:1279-1360`). Non-onboarding builds wait for review; confirmed onboarding builds prune invalid assets and publish automatically only after validation (`apps/api/src/assistant.ts:1362-1459`).
8. Publication rechecks the proposal hash, every input version, the base generation, and editor authority; stages new objects/edges/assets under a fresh generation; then atomically advances the workspace generation pointer and writes publication/audit records (`apps/api/src/assistant.ts:1478-1514`; `apps/api/src/assistant.ts:1571-1691`; `apps/api/src/assistant.ts:1692-1787`).

### Data stores

- **HelixDB:** All metadata is represented as generic `FoundryRecord` nodes containing JSON documents, indexed by unique key, scope, and scope-plus-kind; relationship resources also create native `FoundryRelationship` edges (`apps/api/src/store.ts:46-73`; `apps/api/src/store.ts:92-121`; `apps/api/src/store.ts:198-241`). Writes use a per-scope revision node as an optimistic-concurrency guard, and transactions retry conflicts five times before returning HTTP 409 (`apps/api/src/store.ts:130-170`; `apps/api/src/store.ts:345-359`).
- **Filesystem/Parquet:** Complete versions are written beneath the configured data directory; incoming files and per-job DuckDB scratch directories are separate (`services/executor/src/engine.ts:27-49`; `services/executor/src/engine.ts:51-77`; `services/executor/src/engine.ts:137-138`). The product has no automatic artifact garbage collector (`docs/OPERATIONS.md:29`).
- **In-memory store:** Tests and isolated browser acceptance can substitute `MemoryStore`, which implements the same list/get/version/commit/neighbors contract (`apps/api/src/store.ts:270-305`; `docs/onboarding.md:40-44`).

### Model and agent-facing interfaces

- `ModelProvider` is a small structural interface: `generate(system, context, schema, signal) -> {value,tokens}` (`packages/shared/src/index.ts:144-157`). The concrete `Provider` maps it to Ollama constrained JSON, Anthropic tool use, or OpenAI Responses JSON Schema (`apps/api/src/providers.ts:10-93`; `apps/api/src/providers.ts:94-140`). This is a provider switch inside one class, not a plug-in registry.
- Calls are bounded by per-run call count and elapsed time plus a per-workspace daily token budget; completed structured stages are checkpointed and reused when the input-version hash is unchanged (`apps/api/src/assistant.ts:580-605`; `apps/api/src/assistant.ts:606-678`).
- The agent/developer surface is HTTP/OpenAPI plus the TypeScript SDK, not MCP (`docs/API.md:1-5`; `apps/api/src/openapi.ts:20-45`; `packages/sdk/src/index.ts:69-96`). The repository's `AGENTS.md` is an installation runbook for coding agents, not an application protocol; the README tells a user to hand that runbook to Claude Code, Codex, Cursor, or another terminal-capable agent (`README.md:18-34`).

## 3. Notable patterns and abstractions

### Retrieval, search, ranking, embeddings, indexing, and memory

- **No Acheron-like retrieval stack.** There is no document chunking, embedding generation, vector store, query expansion, hybrid retrieval, reranking, or MCP tool implementation. INFERRED from the complete tracked-source term search and the actual service/interface inventory (`docs/GUIDE.md:127-150`; `docs/API.md:1-5`). “Memory” in the code means an in-memory DuckDB database or test store, not agent memory (`services/executor/src/engine.ts:41-49`; `apps/api/src/store.ts:270-305`).
- **Literal resource search.** `GET /resources/:kind` loads the scoped collection, filters by a lowercase JSON substring over name/description/effective data, optionally applies exact object-field equality, sorts, and only then slices for pagination (`apps/api/src/app.ts:301-362`; `apps/api/src/app.ts:363-399`). This is linear collection scanning, not indexed relevance ranking; the docs acknowledge that large ontology deployments need storage-level pagination (`docs/VALIDATION.md:63`).
- **HelixDB indexing is metadata lookup, not semantic indexing.** The store creates equality indexes on `key`, `scope`, and `scopeKind`; reads retrieve JSON documents by those exact attributes (`apps/api/src/store.ts:60-73`; `apps/api/src/store.ts:92-128`).
- **Ontology matching is the closest ranking mechanism.** Candidate key columns are compared by exact and case-insensitive value overlap in a generated DuckDB value index (`apps/api/src/discovery.ts:1011-1053`). Edges are accepted by explicit coverage thresholds, labeled with declared/name/value evidence, and ordered by exact matches, evidence rank, coverage, then deterministic lexical tie-breaker (`apps/api/src/discovery.ts:367-440`; `apps/api/src/discovery.ts:462-471`). Direct links implied by a two-hop path are removed only when at least 95 percent of rows agree (`apps/api/src/discovery.ts:939-1008`). These are deterministic relational heuristics, not learned ranking.

### Provenance and citations

- Every dataset version is an immutable resource tied to a Parquet filename and profile; refreshed datasets keep a version history, with schema-changing versions staged rather than silently activated (`apps/api/src/datasets.ts:47-79`).
- General queries return `citations` as `(datasetId, version)` and identify state as `dataset_snapshot` (`apps/api/src/datasets.ts:162-210`). Analyst answers add the human-readable dataset name to the same version citation and persist the executed rows plus assumptions (`apps/api/src/assistant.ts:893-963`).
- Validation reports record exact `inputVersions`, validation time, base generation, executed checks, and previews; proposal hashes cover the bundle plus those versions and generation (`packages/shared/src/index.ts:128-143`; `apps/api/src/assistant.ts:65-72`). Publication refuses stale data, stale definitions, a changed proposal hash, or changed authority (`apps/api/src/assistant.ts:1486-1512`; `apps/api/src/assistant.ts:1692-1718`).
- Published derived datasets receive lineage resources recording each input and its active version (`apps/api/src/assistant.ts:1516-1560`).

### Schemas and validation

- Zod is the shared contract system. It constrains provider settings and budgets, bundles and asset counts, onboarding state, ontology evidence, and API bodies; OpenAPI converts those same schemas to JSON Schema (`packages/shared/src/index.ts:71-127`; `packages/shared/src/index.ts:229-354`; `apps/api/src/openapi.ts:20-45`; `apps/api/src/openapi.ts:46-121`).
- Model output is provider-native structured output and then parsed again by Zod. For OpenAI, optional fields are transformed into nullable required fields with `additionalProperties: false`; for Ollama, unbounded arrays are capped at 12 to reduce small-model loops (`apps/api/src/providers.ts:190-220`; `apps/api/src/assistant.ts:652-678`).
- Validation is executable: pipeline SQL runs and persists a preview, quality-check queries must return truthy results, ontology keys must be unique/non-null, relationship coverage is measured, dashboard queries run, and action fields are checked against the ontology (`apps/api/src/assistant.ts:175-245`; `apps/api/src/assistant.ts:246-338`).
- Visual pipeline graphs compile by depth-first traversal into common table expressions, rejecting duplicate node identifiers, cycles, invalid arity, and multiple output leaves (`packages/shared/src/pipeline.ts:6-25`; `packages/shared/src/pipeline.ts:29-100`).

### Provider and connector abstractions

- The model abstraction is portable and small, but the implementation branches on three hard-coded provider names in one class (`packages/shared/src/index.ts:150-157`; `apps/api/src/providers.ts:28-93`). There is deliberately no provider fallback; protocol tests assert that behavior (`tests/providers.test.ts:8`; `tests/providers.test.ts:147`).
- Data connectors share `discover(kind, config)` and `importSource(scope, kind, config, progress)` functions, but dispatch is also a hard-coded `if` chain rather than registration-based plug-ins (`apps/api/src/connectors.ts:81-203`; `apps/api/src/connectors.ts:208-221`; `apps/api/src/connectors.ts:394-428`). They enforce bounded listings/imports and source-specific normalization, with a two-million-record snapshot limit (`apps/api/src/connectors.ts:153-179`; `apps/api/src/connectors.ts:237-247`).

### Job execution and sandboxing

- Durable jobs/runs use explicit status, lease expiry, attempts, retry time, progress/events, and a 30-second heartbeat; expired leases are reclaimable (`apps/api/src/jobs.ts:68-109`). Unknown job types fail explicitly rather than being reported as successful (`apps/api/src/jobs.ts:125-140`).
- DuckDB runs per job in an operating-system child process, in-memory, with two threads, 512-megabyte default memory, 2-gigabyte scratch, disabled unsigned/auto extensions, disabled external access, locked configuration, and exactly one `SELECT`/`WITH` statement wrapped into a result table (`services/executor/src/engine.ts:41-49`; `services/executor/src/engine.ts:120-131`). Only declared Parquet inputs are loaded (`services/executor/src/engine.ts:79-119`).
- Container defense adds an internal-only network, a 2-gigabyte memory cap, 128-process cap, all Linux capabilities dropped, and `no-new-privileges` (`compose.yaml:50-63`; `compose.yaml:98-100`).

### Evaluation and benchmark harnesses

- Unit/API/workflow tests run under Vitest with 120-second timeouts, fork isolation, and serial files; browser acceptance uses Playwright, one worker, retained failure traces, and isolated API/executor/Vite servers (`vitest.config.ts:1-9`; `playwright.config.ts:1-41`).
- Coverage includes executor isolation and profiling (`tests/engine.test.ts:22-78`), workspace/token/origin boundaries (`tests/api.test.ts:35-358`), model routing and hosted-context masking (`tests/assistance.test.ts:62-245`), deterministic ontology discovery and false-match defenses (`tests/discovery.test.ts:108-650`), durable lease recovery (`tests/jobs.test.ts:24-76`), and complete browser onboarding/workspace flows (`tests/browser/onboarding.spec.ts:5`; `tests/browser/onboarding.spec.ts:160`; `tests/browser/workspace.spec.ts:12`).
- The benchmark creates one million JSONL rows, measures ingestion, then sends 25 concurrent grouped-aggregation queries either in-process or through the HTTP executor; it explicitly excludes inference and reports only the benchmark client's resident memory (`scripts/benchmark.ts:1-16`; `scripts/benchmark.ts:30-66`). The checked-in Apple M1 Pro result reports 472.4 milliseconds ingestion, 1,689.7 milliseconds median response, and 3,138.7 milliseconds maximum response (`docs/benchmarks/local-m1-pro.json:1-11`).

### Observability, caching, and configuration

- Fastify structured logs redact authorization, cookies, passwords, API keys, and connector configs, and omit query strings from logged URLs (`apps/api/src/app.ts:63-84`). Runs/jobs retain structured stage events, calls, tokens, progress, errors, and findings; the workspace offers authenticated server-sent event updates (`apps/api/src/assistant.ts:453-470`; `apps/api/src/jobs.ts:142-175`; `apps/api/src/routes/workspace.ts:434-439`). No OpenTelemetry, distributed tracing, metrics exporter, or external log backend is implemented in the inspected source. INFERRED from the logging and event implementations just cited.
- Reuse is signature-based rather than a general cache: model stage checkpoints survive retries only for the same input-version hash (`apps/api/src/assistant.ts:543-548`; `apps/api/src/assistant.ts:580-678`), onboarding recommendations/suggestions are keyed by input signatures (`apps/api/src/onboarding-state.ts:95-189`), and Home metrics coalesce concurrent loads and regenerate on schema-signature changes (`apps/api/src/metrics.ts:725-769`).
- Runtime configuration is environment-based: ports/hosts, origins, HelixDB/executor/Ollama endpoints, keys, data directory, inline-worker mode, and rate limit (`apps/api/src/config.ts:1-24`; `.env.example:1-20`). Provider budgets live in validated per-workspace settings (`packages/shared/src/index.ts:71-82`).

### Access control

- The product has no login boundary: absence of an authorization header means the local owner, so network isolation is part of the security model (`apps/api/src/app.ts:35-39`; `apps/api/src/app.ts:137-152`; `README.md:155-163`). Host checks mitigate Domain Name System rebinding, browser mutations require the configured origin, and rate limiting defaults to 240 requests per minute per IP (`apps/api/src/app.ts:121-134`; `apps/api/src/config.ts:17-18`).
- API tokens are hashed for lookup, workspace-scoped, optionally read-only, revocable, and checked against viewer/editor/owner roles (`apps/api/src/app.ts:137-177`). Public resource serialization removes secrets and job file paths (`apps/api/src/onboarding-state.ts:8-12`).

## 7. Unknowns, broken/stubbed behavior, and aspirational claims

- **No independent execution in this review.** I did not install dependencies, build, run tests, start containers, or call live services, per the read-only constraint. All behavior above is code-grounded; validation performance claims are repository-authored evidence, not independently reproduced (`docs/VALIDATION.md:1-4`).
- **Hosted model validation is fixture-only.** The repository says no Claude/OpenAI credentials were available for live checks; only their protocols were tested (`docs/VALIDATION.md:57-60`).
- **Capacity certification is incomplete.** Peak combined memory on the stated 16-gigabyte target and an 8-gigabyte installation remains unverified; the million-row benchmark does not certify million-object publication (`docs/VALIDATION.md:59-60`).
- **Connector coverage has gaps.** Deployment-specific certificate chains and a real S3 service still require environment integration testing (`docs/VALIDATION.md:61`). Hosting-provider OAuth also requires external provider approval/configuration and real authorization/import checks beyond mocks (`docs/HOSTING.md:19-25`; `docs/HOSTING.md:41`).
- **Search/storage scalability is limited.** Metadata pagination currently loads a whole scoped collection before slicing, the ontology graph shows only the first 100 objects, and record/relationship selectors use fixed-size pages (`docs/VALIDATION.md:63`; `apps/api/src/app.ts:301-399`). There is no artifact garbage collector (`docs/OPERATIONS.md:29`).
- **Change-data capture is snapshot materialization, not delta application.** The code/docs describe native PostgreSQL/MySQL log capture that coalesces changes into complete new snapshots; row deltas are not applied directly (`docs/GUIDE.md:103-107`; `docs/OPERATIONS.md:17-21`). This can lag on large or rapidly changing tables (`docs/GUIDE.md:105`).
- **The validation document contains stale contradictions.** It claims verified owner bootstrap, local sessions, one-use invitations, role checks, and scoped tokens (`docs/VALIDATION.md:7-10`), while the current product explicitly has no accounts/sign-in and provisions a single local owner (`apps/api/src/app.ts:35-39`; `apps/api/src/app.ts:206-267`). No invitation route appears in the current API reference (`docs/API.md:9-92`). It also says the release “does not provide ... CDC” (`docs/VALIDATION.md:67`), contradicting the implemented/documented change-stream path (`apps/api/src/jobs.ts:24-25`; `apps/api/src/source-sync.ts:291-588`; `docs/OPERATIONS.md:17-21`). Treat those validation sentences as stale, not current capabilities.
- **Some features are explicitly not implemented.** There is no automatic artifact collection (`docs/OPERATIONS.md:29`), no direct row-delta CDC application (`docs/GUIDE.md:105`), and no source write-back, per-row model enrichment, distributed compute, distributed transactions, single sign-on, billing, or external-source transaction coordination (`docs/GUIDE.md:107`; `docs/VALIDATION.md:64-67`).
- **Ontology/model semantics remain review-dependent.** Executed validation proves structural and query correctness, not business meaning; ambiguous joins and business assumptions still require human review (`docs/GUIDE.md:123-125`; `docs/VALIDATION.md:64-65`).
- **Single-node assumptions are hard boundaries.** The supported release expects one person, one worker replica, two concurrent executor children, and loopback-only exposure (`docs/OPERATIONS.md:31-35`; `apps/api/src/server.ts:6-12`). Behavior under horizontal scaling, multi-user tenancy, or network exposure is not established.
- **No MCP or agent-memory portability layer exists.** Any relevance to Acheron is therefore at the level of isolated patterns—snapshot citations, executable validation, deterministic evidence labels, resumable leases/checkpoints, and sandbox boundaries—not an implemented memory/retrieval component.
